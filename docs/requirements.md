## 1. Бизнес-цели и метрики

| ID | Цель | Метрика успеха (KPI) |
| :--- | :--- | :--- |
| **BG-01** | Минимизация времени поиска | Время от получения запроса сервером до отправки первого токена ответа (TTFT) **< 3.0 секунд**. |
| **BG-02** | Качество ответов | Бот должен предоставить корректный ответ (совпадающий с эталонным) для **80%** сценариев из тестового набора "Golden Set". |

## 2. Функциональные требования

### 2.1. Загрузка и Обработка данных (Ingestion)
| ID | Требование | Спецификация | Критерий приемки |
| :--- | :--- | :--- | :--- |
| **FR-01** | Очистка формата MDX | Система **должна** удалять JSX-компоненты (теги `<... />`, импорты `import ...`) из файлов `.mdx`, сохраняя только текстовый контент и Markdown-разметку. | Парсинг файла с `<Alert>Info</Alert>` возвращает только текст "Info". |
| **FR-02** | Сохранение метаданных | При нарезке (Chunking) система **должна** сохранять в метаданные вектора: путь к файлу, номер страницы (для PDF) или заголовок секции (для MD). | Метаданные в Chroma содержат поля `source`, `page`, `section`. |
| **FR-03** | Стратегия векторизации | Размерность вектора **строго равна 768** (Nomic Embed v1.5). Использование Matryoshka (срез до 256) допускается только на этапе чернового поиска, но хранение — полное. | Проверка: `len(embedding) == 768` для записей в коллекции Chroma. |
| **FR-04** | Дедупликация | Система **не должна** повторно обрабатывать файлы, MD5-хэш контента которых совпадает с записью в реестре индексации. | Лог повторного запуска скрипта `ingest.py` содержит записи "Skipped (Unchanged)". |

### 2.2. Поисковый движок (Retrieval Engine)
| ID | Требование | Спецификация | Критерий приемки |
| :--- | :--- | :--- | :--- |
| **FR-05** | Двухступенчатый поиск | 1. Получение 20–50 кандидатов из Chroma (Dense: cosine).<br>2. Переранжирование (Cross-Encoder) и отсечение кандидатов с `score < 0.5`. | В контекст LLM попадают только документы, прошедшие порог Cross-Encoder. |
| **FR-06** | Расширение запроса (HyDE) | Для всех запросов, не содержащих явного указания на код ошибки (regex `\b[A-Z]{3}-\d{3}\b`), применять генерацию гипотетического документа. | Запрос "VPN не работает" порождает промежуточный запрос с техническими терминами ("OpenVPN", "config", "timeout"). |
| **FR-07** | Бюджет контекста (Context Budgeting) | Суммарный объем контекста (Найденные чанки + История + Few-Shot) **не должен превышать 12,000 токенов** (для гарантии скорости и экономии). При превышении — отбрасывать старые сообщения истории, затем чанки с низким рангом. | Ошибка `context_length_exceeded` не возникает при стресс-тестах. |

### 2.3. Генерация (Generation & Prompting)
| ID | Требование | Спецификация | Критерий приемки |
| :--- | :--- | :--- | :--- |
| **FR-08** | Chain-of-Thought (CoT) | Системный промпт **должен** требовать от модели рассуждения по шагам перед ответом (формат: `Thought: ... Answer: ...`). | Ответ модели в логах содержит секцию рассуждений. |
| **FR-09** | Few-Shot Learning | Промпт **должен** включать минимум 2 статических примера пар "Вопрос - Контекст - Идеальный Ответ" в стиле документации QuantumForge. | Примеры жестко зашиты в шаблоне промпта. |
| **FR-10** | Атрибуция (Citations) | Модель **должна** указывать источник для каждого утверждения или в конце ответа в формате `[Файл: имя]`. | Ответ без ссылок считается браком (Fail). |
| **FR-11** | Защита от галлюцинаций | Если после Reranking не найдено ни одного чанка с `score > 0.5`, система **должна** вернуть заглушку: "В базе знаний нет информации по вашему запросу", не обращаясь к LLM. | Экономия вызова LLM при пустом поиске. |

### 2.4. Телеметрия и Логирование (Observability)
| ID | Требование | Спецификация | Критерий приемки |
| :--- | :--- | :--- | :--- |
| **FR-12** | Схема логирования | Каждый запрос фиксируется в `logs.jsonl` со структурой:<br>`{"timestamp": ISO8601, "query": str, "retrieved_docs": List[str], "generation_time_ms": int, "model_answer": str, "tokens_used": int}`. | Файл логов валидируется JSON-схемой. |

## 3. Нефункциональные требования (NFR)

### 3.1. Безопасность (Security)
| ID | Требование | Спецификация | Критерий приемки |
| :--- | :--- | :--- | :--- |
| **NFR-01** | Изоляция контекста (Injection Defense) | Контент найденных документов оборачивается в XML-теги `<search_result>`. Системный промпт явно запрещает исполнение инструкций внутри этих тегов. Из текста документов удаляются подстроки: "Ignore all instructions", "System prompt". | Атака через "отравленный" документ не меняет поведение бота. |
| **NFR-02** | Маскирование PII | Перед отправкой в API Gemini, текст проходит через PII-фильтр (Regex для MVP, Presidio — опционально для офлайн-аудита). Паттерны: Email, IPv4, Phone. Замена на `<REDACTED>`. | В трафике к Google API нет чувствительных данных. |

### 3.2. Интерфейс (Telegram UX)
| ID | Требование | Спецификация | Критерий приемки |
| :--- | :--- | :--- | :--- |
| **NFR-03** | Асинхронность | Использование `aiogram` в асинхронном режиме. Блокирующие операции (HTTP requests, DB queries) выполняются в `await`. | UI не "фризится" при одновременной работе 5 пользователей. |
| **NFR-04** | Индикация прогресса | Отправка `ChatAction.TYPING` каждые 4-5 секунд во время генерации. | Пользователь видит статус "печатает..." до момента ответа. |

## 4. Ограничения реализации
*   **C-01**: ChromaDB Persistent Storage обязателен (локальный каталог `data/chroma_storage`).
*   **C-02**: Использование локальных эмбеддингов (без API OpenAI Embeddings).
*   **C-03**: Бюджет на API LLM < $50/мес (Gemini 3 Flash ~$37/мес при 500 запросов/день).
*   **C-04**: Redis для кэширования сессий и семантического кэша (опционально для MVP).
